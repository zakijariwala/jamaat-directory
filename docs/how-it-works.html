Data flow

One pipeline, two exits for a phone number

Intake and moderation stay in Google, where non-technical moderators work. An approved row is signed and pushed to the site; nothing is polled. Phone numbers live only in D1 and leave it one at a time through /api/reveal — they never appear in the public directory.json.

Page building

Two builds run at different times, from different sources

This is the crux. The data is always live from D1; the HTML pages are generated at deploy time from the seed file. A city added through the Form lands in D1 and shows in directory.json immediately — but its rendered page waits for a build.

Adding a city

Thane in full, Mumbra in part

Both travel the same pipeline. Partial data needs no special case — the city page renders a section only when it has rows, and the status chips grey out what’s missing.

What each page renders

  • Thane all 5 chips — Contacts, Masjid, Musafir khana, Dining, Hotels.
  • Mumbra masjid only — just the Masjid section; Contact / Stay / Hotels / Food chips render greyed. No empty headings, no blank cards.
  • In the home index both sit under Maharashtra (alphabetical: Mumbra, then Thane); Mumbra’s icon row shows the mosque lit and the rest muted — “honestly marked.”

The /api/ingest endpoint already accepts facilities; the sample Apps Script currently maps city + one contact, so submitting Thane’s masjid/musafir/hotel via the Form means extending that column map — planned after the Cloudflare prototype is deployed and tested.

De-duplication

Identity is the primary key

Every row upserts with INSERT OR REPLACE keyed on its id. So de-duplication is entirely about how ids are assigned.

City

Identity is the slug (cities.id, e.g. thane). Re-submitting Thane overwrites the same row — no duplicate city. Alternate spellings (Thana / Thane, Mumbra / Mumbrah) are not new cities; they go in aliases[] so search resolves them while the slug stays the one identity. The moderator assigns the canonical slug in the Sheet — that’s what prevents split cities.

Contact / Masjid / Facility

Identity is its id. Editing the same Sheet row re-sends the same id → idempotent. But two different submissions of the same masjid get two ids → two entries. There is no automatic “same name = same masjid” merge.

Removal

A removal request sets status = 'removed'; the entry simply drops out of the next buildSnapshot().

By design Name-based de-duplication is the moderator’s job in the Sheet — which is exactly why the Sheet stays the moderation surface. Want re-submissions of the same masjid to auto-merge? Give facilities a deterministic id like f-thane-masjid-<slug-of-name> instead of a row-derived one; then a second “Thane Jame Masjid” upserts onto the same row. Today’s scheme favours moderator control over automatic merging — a deliberate, changeable trade-off.
